## 1. What was built

**Reusable Legal Aid Clinic Mode, enabled for MVLP only.** An additive layer on the existing Clinic Mode: an event carries `experience = 'legal_aid'` and a partner-approved policy profile; Standard Clinic Mode events, screens, RPCs and verifiers are unchanged. Only the `mvlp` partner slug has branding and a profile template, so no other organization can reach the experience by URL.

**MVLP co-branded website.** `public/mvlp-landing.html` is generated from the shipped We Must Vote template (`public/wemustvote-landing.html`) by `scripts/partners/build-mvlp-landing.mjs` (deterministic; `--check` guards drift and refuses any We Must Vote, Wilma or internal vocabulary). Same layout and sections, MVLP wordmark (transparent margins trimmed non-destructively; original kept beside it), measured purple `#6D378F` with derived shades, program copy and FAQ that distinguish MVLP attorney advice from courtroom representation, actions **Register for a clinic** → `/p/mvlp/clinics` and **Continue my application** → `/p/mvlp/continue`. Served for `/p/mvlp` on the `legaleasepartner.com` hosts by `src/proxy.ts` (`shouldUseStaticMvlpLanding`, exact path only); other hosts render the React template through an explicit MVLP configuration in `src/lib/partners/landing-page.ts`. The We Must Vote path and all other partner outputs are unchanged (`scripts/verify-we-must-vote-launch.mjs` passes).

**Registration.** `/p/mvlp/clinics` lists published legal-aid events from saved configuration in `America/Chicago`. `/clinic/<slug>/register` requires the participant's own authenticated LegalEase account, collects name, contact method, language and assistance needs only, and calls `legal_aid_register`, which decides capacity, window, waitlist and duplicates atomically with an idempotency key (a retried submit returns the same row). Participants may cancel; staff set confirmed/waitlisted/declined.

**Confidential intake.** `/clinic/<slug>/intake`: ten steps from the 52-field map (`src/lib/legal-aid/intake-schema.ts`; every observed leaf documented in `MVLP_INTAKE_FIELD_MAP.md` as observed, adaptation or unresolved), server-side autosave with version conflict detection, "I don't know" for money fields, conditional home/vehicle/account questions, no defaults for income, assets, household or citizenship. The Social Security number has its own protected step and API (`/api/legal-aid/intakes/<id>/restricted`): AES-256-GCM with the key from `LEGAL_AID_RESTRICTED_FIELD_KEY` (versioned, rotatable through `LEGAL_AID_RESTRICTED_FIELD_KEY_<VERSION>`), stored in `legal_aid_restricted_fields` with no browser-role policy, only the last four digits kept beside it, revealed only by the assigned attorney or coordinator with a recorded purpose. Applicants sign the statements that apply (financial statement; the verbatim citizenship statement only when the answer is Yes; a confidential-review acknowledgment when No; an information-sharing consent), typed or drawn, with statement version and hash, answer version and hash bound to each signature; a material edit supersedes every signature; the signer must be the applicant. Submission is a separate act that creates the linked `clinic_cases` row. Uploads go to the private bucket `rcap-legal-aid-private` with magic-byte validation, write-once keys and an audited, server-streamed, no-store download.

**Staff review.** `/clinic/staff/<eventId>/applications` and `/…/<intakeId>`: roles are event-scoped permissions on the existing `clinic_event_staff` record (`coordinator`, `intake_review`, `program_review`, `attorney`, `notary`, `follow_up`, `reporting`, `export`), assigned by email on `/partner/clinic/<eventId>/legal-aid`. Screens: information requests, start review, attorney assignment, decisions (program eligibility, attorney review, conflict/engagement, each with its own outcome set and a written reason), financial summary (countable cash income from the approved profile; food benefits reported but never counted; no guideline table in the template, so the outcome is always **Needs a person's decision**; expenses never deducted), answers, audited reveal, documents, court-document execution, next steps, participant messages, case-file export, external case reference. Every staff view of an application is written to `legal_aid_access_audit`.

**Documents, execution, follow-up, export.** A document task is created from the participant's own prepared packet (`packet_render_jobs`, bound by the artefact hash; the unsigned reviewed copy is streamed to the attorney, coordinator or notary through `/api/legal-aid/staff/intakes/<id>/unsigned/<task>` after an owner and hash check) and moves in database-enforced order: draft → attorney reviewed → ready for execution → signature or notary pending → executed copy received (requires an uploaded executed document) → execution reviewed → ready to file → filed (recorded by the coordinator or follow-up volunteer). No seal, notary block or signature is ever generated. Follow-up uses the existing follow-up record and Resend delivery; the communication state reports what happened (`sent` with the provider id, `failed`, or `no_contact`). Case-file export produces JSON and PDF into the private bucket, always masked at rest; an export flagged as including the protected value adds it only when an attorney or coordinator downloads it, through the audited reveal. The three outputs stay separate: the MVLP case file, the court packet (existing packet path), and the participant's instructions (their own application page).

## 6. Known limitations and decisions

- The public page and screens exist for the `mvlp` slug only; the React fallback for other hosts still requires the partner record to be authoritatively published.
- The policy profile template deliberately carries no income guideline; installing one is a new approved profile version, never a code change.
- Registration by staff on a participant's behalf exists in the database RPC (`source = 'staff_assisted'`) but has no screen; participants register on their own account, with help.
- Participant messages send only when Resend is enabled in the environment; the screen always reports the real state.
- The participant sign-in screen is the shared LegalEase account screen ("Sign in or create your account").
- `package.json` gained the new verifiers on `npm test` and `verify:legal-aid:e2e`; this, like every change under `src/`, changes the worker image inputs (section 4, item 4).
