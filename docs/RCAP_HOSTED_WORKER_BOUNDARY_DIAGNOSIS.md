Tools SHA on main: `a1d345a671033d4c783c4d970e84d7fe775d14f9`.
Application freeze: `664b8ddd374642bf2bd1820f7e05224f3dd081bc`.

## 1. What the run actually preserved, and what it destroyed

The line the matrix printed for the worker was:

```
ok   worker_renders_and_stores_the_artifact — ghcr.io/…@sha256:be782397… exited 0;
     the job for this item is 'claimed' after 1 attempt(s). Tail: e
```

`Tail: e` is not a truncation of the message. The harness computed
`` `${run.stdout}${run.stderr}`.slice(-260) ``, docker writes image-pull progress
to stderr, and the last 260 characters of the concatenation were therefore the
pull progress — one trailing character of a line, then `Pull complete`, `Digest:`
and `Status:`, which is why those three lines appear in the run log immediately
after the verdict. The worker runs `--once`, and `--once` prints exactly one
line: `JSON.stringify(runWorkerCycle(...))`, the object that names the boundary
the cycle stopped at. It was produced on stdout, pushed to the front of the
concatenation, and cut away.

**The single diagnostic that names the failure was generated by the worker and
discarded by the acceptance harness.** That is a harness defect, and it is why
the boundary cannot be read off this run.

Both streams are now captured separately and in full, per cycle, and written to
`hosted-acceptance-evidence/worker-console.log` and
`hosted-acceptance-evidence/worker-diagnostics.json`, which the workflow already
uploads as a run artifact.

## 2. What the observed database state does and does not narrow

Observed after the single worker invocation: `status = 'claimed'`,
`attempt_count = 1`, `output_storage_path` null, zero stored bytes.

`runWorkerCycle` (`src/lib/rcap/render/render-worker.ts`) has exactly seven exits.
Each leaves a distinct terminal state:

| exit | leaves the job | matches the observation |
| --- | --- | --- |
| `claim()` returns null (`outcome: "idle"`) | untouched, `queued` | no — the job was claimed |
| `assertClaimAcceptable` throws → `fail(retryable=false)` | `failed` | no |
| `startRender` returns false (`job_not_claimable`) | **`claimed`** — `fail()` is never called | **yes** |
| render or validation fails → `fail(retryable=true)` | `failed` | no |
| `startValidation` returns false | `rendering` | no |
| upload or re-read fails → `fail(retryable=true)` | `failed` | no |
| `finalize` returns null | `validating` — `fail()` is never called | no |
| any throw → catch → `fail(retryable=true)` | `failed`, **unless the `fail()` call itself errors** | only in that sub-case |

So the observation is consistent with exactly two things: `startRender` returned
false, or an exception occurred and the `fail()` RPC that should have recorded it
also failed at the transport layer. Every other exit is excluded by the state.

## 3. The database contract is not the cause

`scripts/verify-rcap-consumer-lifecycle-boundaries.mjs` boots an ephemeral
PostgreSQL 16 cluster, applies the authorized migration sequence (49 → 55), and
walks one consumer matter of the same shape through the worker's own sequence.
All fourteen checks hold:

- `claim_packet_render_job` → `claimed`, fencing token issued, `attempt_count` 1;
- `start_packet_render` on that freshly claimed job → **true**, job `rendering`;
- `start_packet_validation` → true, job `validating`;
- `finalize_packet_render_job` → `zero_charge` / `eligible`, job `artifact_validated`;
- `fail_packet_render_job` from `claimed` → `retryable`, job **`failed`**.

The phase-50 authority guard, the phase-49 transition guard, the phase-52
immutability trigger and the phase-55 paid-matter guard all admit this sequence.
**Classification D — a database contract or transition defect — is excluded by
proof, not by inference.** A worker left holding a claim is not being refused by
this contract.

That leaves classification C (a worker runtime defect) and classification B (a
missing or wrong acceptance environment configuration) live, and they are not
separable from this run because of §1. Two configuration facts are relevant and
have been corrected: the container was given no `RCAP_WORKER_CLAIM_SECONDS`, so
its lease was the 600-second default, and the harness ran exactly one cycle and
read the job immediately. Under those two settings a single declined RPC — for
any reason, including a transient — produces precisely the observed state with no
recovery possible inside the run. The matrix now shortens the lease through the
worker's own documented environment contract and runs the cycle up to four times,
waiting on whichever of `claim_expires_at` or `next_attempt_at` the queue is
itself waiting on, so a transient and a defect no longer look identical.

## 4. Where each record is actually created

Proved by the same lifecycle verifier, not assumed:

| record | expected boundary | actual boundary | in run 32185795181 | verdict |
| --- | --- | --- | --- | --- |

| matter-level payment consumption | — | **`finalize_packet_render_job`** (phase 52) | absent | correct — nothing had finalized |
| entitlement / packet-credit accounting row | — | **`finalize_packet_render_job`** (phase 52) | absent | correct — nothing had finalized |

Consequences for the four reported failures:

1. **`person_and_matter_are_bound_on_the_render_job` — harness expectation
   defect.** The job carried `person_id=c2b1ec38…` and `matter_id=2d6fd496…`.
   The case compared them against `consumer_packet_payment_consumption`, which
   finalization writes; with no such row the LEFT JOIN produced `(null, null)`
   and the correct binding read as a mismatch. The product was right. The case
   now checks the enqueue-time binding against the item's stored payment binding
   and the database's own derived matter id, and does not touch the accounting
   row.
2. **`artifact_is_stored_privately_and_re_readable` — real.** No artifact
   existed, so nothing could be read back. Independent of the above.
3. **`delivery_serves_the_owner_and_refuses_everyone_else` — real, and the case
   was also too weak.** Owner A got 409, B 404, anonymous 307. The verdict
   ignored the owner entirely and would have passed on the two refusals alone —
   a state in which nobody, including the person who paid, can download. It now
   requires the owner to receive bytes whose sha256 equals the finalized
   artifact's.
4. **`event_replay_creates_no_second_entitlement_or_render_job` — harness
   expectation defect.** Replay returned 200 `outcome=recovered`, render jobs
   1 → 1, entitlements 0 → 0. That is idempotency holding. The case additionally
   demanded `entitlements === 1`, which is a finalization assertion wearing a
   replay case's name. It now compares provider event records, payment records,
   consumption rows, ledger events and render jobs across the replay and
   requires only that none of them move.

So the four were not one cause. Two were the harness asserting finalization
under other names, one was real, and one was real *and* separately unable to
fail.

## 5. Replay idempotency, on its own evidence

The proof does not need an artifact and no longer asks for one. Baseline counts
are taken, the same signed event is redelivered byte-identically with a fresh
timestamp, and the same counts are taken again: provider event records, paid
payment records, matter-level consumption rows, credit-ledger events and render
jobs. Success is a 200 and no movement in any of them. Run 32185795181 already
satisfied every part of that; only the extra finalization clause failed it.
