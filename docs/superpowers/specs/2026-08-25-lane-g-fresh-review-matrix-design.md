# Lane G Fresh Review Matrix Design

## Purpose

Lane G needs a deterministic, independent QA matrix for every real Expungement.ai participant flow before lane A freezes the final candidate. The matrix must remain usable when the candidate SHA changes, must not modify product behavior, and must not replace lane A's canonical release ledger.

The initial authority is commit `714f4d51f93461855b24c8644b6ea6ddad6d15f2`. Fresh Correction Review and hosted browser acceptance will use the later exact SHA supplied by lane A.

## Selected approach

Create a SHA-parameterized, read-only Node.js QA harness. The harness reads committed JSON objects with `git show <sha>:<path>`, joins the current flow manifest to the current final dispositions, validates the denominator, and writes only lane-G-owned QA artifacts.

This approach is preferred over a static snapshot because the same command can regenerate evidence for a later frozen SHA. It is preferred over checking out the candidate because lane G remains on its independent branch and does not alter its worktree to inspect product behavior.

## Inputs

The harness consumes these committed candidate files:

- `data/expungement-ai/flow-audit/flow-manifest.json`
- `data/expungement-ai/flow-audit/phase4-corrections/final-flow-dispositions.json`
- `data/expungement-ai/flow-audit/phase4-corrections/waiting-rule-authority.json`
- `data/expungement-ai/flow-audit/phase4/verdict-matrix.json`

The ownership map is derived from the sprint's approved lane assignments:

- lane B owns flows tied to the 50 approved legal decisions;
- lane C owns correction proposal IDs 1–36;
- lane D owns correction proposal IDs 37–73 and candidate-exact Phase-3-held flows;
- lane A owns unassigned shared/integration corrections and otherwise integrated product behavior;
- lane E owns the cross-cutting Clinic Mode expectation;
- lane F owns environment-held acceptance mechanics;
- lane G remains the reviewer and never becomes a product-behavior owner.

The generated matrix records the source SHA and source paths so lane A can replace or enrich this mapping when its canonical final ledger includes direct decision identifiers.

## Components

### Pure matrix builder

`scripts/expungement-ai/qa/fresh-review-matrix-lib.mjs` will export pure functions that:

- validate and index candidate inputs;
- join exactly 356 disposition rows to exactly 356 real manifest rows;
- derive packet/no-packet treatment;
- derive deterministic desktop and mobile fixture records;
- attach privacy-control requirements;
- attach Clinic Mode expectations;
- assign browser shards without overlap;
- derive the Colorado, Mississippi, and Wisconsin stress set;
- compute a stable content digest.

Pure functions keep Git access and filesystem writes out of the core logic, making invariants directly testable.

### Candidate reader and CLI

`scripts/expungement-ai/qa/build-fresh-review-matrix.mjs` will:

- require `--candidate-sha <sha>`;
- verify the ref resolves to one commit;
- read the candidate objects with `git show`;
- invoke the pure builder;
- write deterministic JSON with a trailing newline;
- support `--check` to compare generated bytes with committed artifacts;
- fail with a precise message for a missing path, malformed JSON, missing join, duplicate flow, wrong denominator, or shard overlap.

### Tests

`scripts/expungement-ai/qa/test-fresh-review-matrix.mjs` will use Node's built-in assertions and small synthetic inputs. Tests will cover:

- exact row joining and required matrix fields;
- packet and no-packet treatment;
- desktop/mobile fixture identity and viewport assignment;
- owner-lane precedence;
- six-shard uniqueness, disjointness, and complete union;
- Colorado-first stress ordering;
- rejection of duplicate, missing, extra, or unmatched flows;
- deterministic output independent of input row ordering.

### Generated QA artifacts

The CLI will write to `data/expungement-ai/qa/fresh-review/`:

- `CURRENT_MATRIX.json` — one row per real participant flow;
- `BROWSER_SHARDS.json` — six state-preserving browser shards, each carrying desktop and mobile fixture IDs;
- `THREE_STATE_STRESS_SET.json` — Colorado first, then Mississippi and Wisconsin;
- `BUILD_SUMMARY.json` — counts, invariants, source SHA, and digest.

These are reviewer artifacts, not canonical product ledgers.

## Matrix row contract

Every `CURRENT_MATRIX.json` row will contain:

- flow ID and flow key;
- state and remedy identifier/label;
- public entry route;
- expected evaluator and effective terminal;
- required screening and packet facts;
- packet/no-packet treatment;
- packet families, packet sets, registry tracks, and forms;
- payment and sponsorship modes;
- Clinic Mode expectation and lane-E ownership;
- deterministic desktop fixture;
- deterministic mobile fixture;
- privacy controls;
- current disposition and reason;
- primary owner lane and owner basis;
- source trace fields.

Desktop and mobile fixtures reuse the candidate's real synthetic answer set and differ only by stable fixture ID and viewport. The harness will not manufacture scenario buttons or change answers to force a terminal.

## Browser shard design

The six existing state groups from the authoritative audit are reused to avoid repeating the nationwide audit. Only the 356 real rows are included. Each flow appears in exactly one shard, and both device fixtures travel with that flow.

The stress set is a separate ordered view, not a seventh shard, so it cannot create denominator overlap. Its expected initial counts are Colorado 5, Mississippi 14, and Wisconsin 6 at correction authority `714f4d51…`. Later candidates may change counts only if lane A's canonical ledger explicitly changes the real-flow denominator or route split.

## Privacy and Clinic Mode

Every flow receives stable privacy-control IDs for:

- save/refresh/resume/Back persistence;
- sign-out and prior-history denial;
- cross-user, cross-matter, and cross-tenant denial;
- participant ownership;
- sensitive analytics exclusion;
- packet/private-download authorization where applicable;
- no checkout, credit, or render job for no-packet outcomes;
- End Session / Reset Device and shared-device isolation in Clinic Mode.

Clinic Mode is recorded as a cross-cutting expectation for all nationwide flows. Until lane E is integrated, the status is `pending_lane_e_integration`; after integration, Fresh Correction Review must confirm the same authoritative engine, terminal, packet, payment, and sponsorship behavior.

## Failure behavior

The CLI fails closed. It will not emit partial evidence when:

- the candidate SHA is invalid;
- a required committed input is absent;
- the real-flow count is not 356;
- flow IDs are duplicated;
- a disposition row cannot join to one manifest row;
- a shard is missing a flow or contains overlap;
- either device fixture is missing;
- an owner lane cannot be derived.

Generated files are written only after all validations pass.

## Phase boundaries

Phase 1 ends when the harness, generated current-authority artifacts, focused tests, `--check`, and `git diff --check` pass on lane G.

Phase 2 begins only after lane A supplies an exact frozen candidate SHA. Lane G regenerates the matrix for that SHA, performs the read-only Fresh Correction Review, and returns only `APPROVED_FOR_HOSTED_ACCEPTANCE`, `CORRECTION_REQUIRED`, or `UNREVIEWABLE`.

Phase 3 begins only after lane F provides the exact Preview deployed from the approved SHA. Browser evidence, privacy matrices, the ten-participant shared-device test, and demo cases are not fabricated or marked complete before that handoff.

## Scope exclusions

Lane G will not modify product behavior, canonical ledgers, package or lock files, workflows, migrations, live routes, payment/security guards, or another lane's worktree. It will not deploy Preview or Production and will not repair defects discovered during Fresh Correction Review.
