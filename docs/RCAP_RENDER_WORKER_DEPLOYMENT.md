# RCAP Render Worker Deployment Specification

How the worker stays running outside a developer shell. Nothing here is
deployed by this document; it specifies the artifact and its operation.

| Item | Specification |
|---|---|
| Container definition | `deploy/rcap-render-worker/Dockerfile` |
| Image build | `docker build -f deploy/rcap-render-worker/Dockerfile -t rcap-render-worker:<git-sha> .` — the resulting image digest is the `container_digest` recorded on every finalized artifact |
| Process start | `node scripts/rcap-render-worker.mjs --loop` (container CMD); `--once` exists for smoke runs and cron-style operation |
| Operating model | long-lived `--loop` poller is canonical; each cycle runs housekeeping (`release_expired_packet_render_claims`, `requeue_retryable_packet_render_jobs`) then claims at most one job; 3s idle sleep |
| Deployment target class | a managed always-on container service — single instance, `restart: always`, platform secret store, stdout log drain (Railway service / Fly.io machine class; an ECS task or a supervised container on the staging host also satisfies the contract). Requirements: outbound HTTPS to the Supabase stack only, no inbound ports, no browser. Not serverless and not cron: the loop is long-lived. The remaining deployment decision is the vendor account choice plus provisioning its secrets — everything else is specified here and verified |
| Health check | container HEALTHCHECK (process liveness) plus an operational check: `packet_render_jobs` rows with `status='queued'` and `next_attempt_at < now() - interval '10 minutes'` should be ~0 while a worker is healthy; alert when the oldest claimable job exceeds that age. The queue-age alert is load-bearing: queue-layer errors are swallowed by design, so a worker with unreachable or misconfigured Supabase idles and reports healthy — only the queue-age check exposes it |
| Restart policy | `restart: always` (or the platform equivalent). Crash-safety is proven by the failure-injection suite: an abandoned claim expires, is released or failed retryably, and a retry converges with no duplicate consumption |
| Concurrency | one job per worker cycle; scale by running N containers — `claim_packet_render_job` uses `FOR UPDATE SKIP LOCKED`, so parallel workers never share a job. Start staging with 1; the fencing token makes over-provisioning safe rather than dangerous |
| Lease vs termination | claim lease default 600s (`RCAP_WORKER_CLAIM_SECONDS`); platform kill grace (SIGTERM→SIGKILL) must be shorter than the lease so a terminated worker's claim always expires rather than being half-alive — every platform default (10–30s) satisfies this. Graceful shutdown is implemented in `scripts/lib/rcap-render-worker-loop.mjs`: SIGTERM/SIGINT interrupts an idle sleep immediately, lets an in-flight cycle finish, starts no other, and exits 0. A hard kill mid-cycle is the injected-crash case and converges |
| Environment variables | `NEXT_PUBLIC_SUPABASE_URL`, `SUPABASE_SERVICE_ROLE_KEY` (staging/dev keys only — production secrets never exist on a build machine; the staging deploy uses the platform secret store), `RCAP_WORKER_CONTAINER_DIGEST` (image digest), optional `RCAP_WORKER_CLAIM_SECONDS` |
| Secret source | the deployment platform's secret manager exclusively; no secret in the image, the repo, or a shell profile |
| Least-privilege path | phase 50 creates `rcap_render_worker` (EXECUTE on worker functions only, no table DML). Staging step: mint a Supabase JWT with `role: rcap_render_worker` for the worker instead of the service key, and a storage credential limited to insert + verification reads on `rcap-packet-artifacts-private`. Until then the worker runs on the service key and the storage guarantee is tamper-evidence (re-read verification), not immutability |
| Logs | stdout JSON lines (one per non-idle cycle: outcome, jobId, accountingResult) to the platform log drain |
| Metrics | derived from the job table, which is the source of truth: cycle outcomes, failed_render_jobs_24h (`status='failed'`), terminal backlog (below) |
| Dead-letter / terminal monitoring | `select count(*) from packet_render_jobs where status='failed' and failure_disposition='terminal'` — alert at >0; these never auto-requeue and each needs a human decision through `requeue_packet_render_job_manual(job, authorizer)` |
| Runtime verification | `npm run rcap:verify-render-worker-runtime` proves the operational contract on a real database: graceful drain semantics, claim-lease configuration, terminal and accounting-blocked jobs visible in the cycle log line and in this document's monitoring queries, and temp hygiene (a full render/finalize cycle leaves nothing in the OS temp dir). Crash injection at the claim/render/upload/re-read/finalize boundaries is owned by `verify-rcap-render-worker-delivery.mjs` |

## Selected production execution target (2026-09-16)

The vendor-account decision the table above leaves open is resolved for
production as **one always-on Fly.io Machine**, and everything except the
account itself is now in the repository:

| Item | Where |
|---|---|
| Machine definition | `deploy/rcap-render-worker/fly.toml` — app `legalease-rcap-render-worker`, `shared-cpu-1x` / 1 GB, `restart: always`, no services (no inbound), SIGTERM with a 30 s grace (shorter than the 600 s claim lease), `ENABLE_SUPABASE_PARTNER_DATA=true`, `RCAP_WORKER_CLAIM_SECONDS=600` |
| Deployment control | `.github/workflows/deploy-rcap-render-worker-production.yml` — refuses any tuple other than the frozen candidate's `workerSourceSha` / `workerDigest` as bound by `RELEASE_CANDIDATE_BINDING.json` and the committed publication evidence (publication and image acceptance both `success`); pulls the image from `ghcr.io` by immutable digest, reads back the digest and the OCI revision, mirrors it unchanged into the app's Fly registry (Fly cannot pull a private ghcr.io image), deploys it by the mirrored digest with `RCAP_WORKER_CONTAINER_DIGEST` set to the ghcr digest, then runs the verification below and uploads its evidence |
| Operational verification | `scripts/verify-rcap-production-worker-execution.mjs` — Fly Machines API: exactly one machine, `started`, exact mirrored image digest and OCI revision, exact exported digest, restart-always, no services, ≥ 1 GB; Supabase Management API (read-only, aggregate counts only, no customer row): no claimable job older than the 10-minute alert threshold and an empty terminal backlog |
| Image binding | the same `ghcr.io/roger-legalease/rcap-render-worker@sha256:…` digest the hosted acceptance ran and the production smoke pulls; the mirrored copy is byte-identical layers and config, and `RCAP_WORKER_CONTAINER_DIGEST` records the ghcr digest on every finalized artifact |
| Secrets — repository (GitHub Actions) | `FLY_API_TOKEN` (a Fly *deploy* token scoped to the app), plus the existing `SUPABASE_ACCESS_TOKEN` for the read-only queue check |
| Secrets — Fly app secret store (owner sets once, values never enter the repository or a workflow log) | `NEXT_PUBLIC_SUPABASE_URL`, `SUPABASE_URL` (both the production project URL), `SUPABASE_SERVICE_ROLE_KEY` (the production service-role key; the least-privilege `rcap_render_worker` JWT replaces it when that staging step lands). The deploy control checks these **names** exist before deploying and never reads their values |
| Cost | Fly.io pay-as-you-go: a `shared-cpu-1x` 1 GB Machine is about US$5.70/month plus a few cents of registry storage; no other purchase |
| Owner actions (one time) | 1. Create or sign in to a Fly.io account with a payment method. 2. `flyctl apps create legalease-rcap-render-worker`. 3. `flyctl secrets set NEXT_PUBLIC_SUPABASE_URL=… SUPABASE_URL=… SUPABASE_SERVICE_ROLE_KEY=… --app legalease-rcap-render-worker` (production values, entered locally, never in chat). 4. `flyctl tokens create deploy --app legalease-rcap-render-worker` and store it as the repository Actions secret `FLY_API_TOKEN`. After that the deployment control is dispatchable by the release captain and re-runnable for every successor image |
| Why not the alternatives | Vercel has no long-lived process class; GitHub-hosted runners are not a production service and consume Actions minutes as a loop; Railway satisfies the same contract at a similar price but needs registry credentials configured in its UI for a private ghcr.io image — Fly's app-scoped registry keeps the whole path inside the deploy token |
