## What is deliberately absent from the patch

No provenance key recording the decision is added. The verifier imposes no
exact-key constraint on `provenance`, so a `profileSha256Decision` key would
apply cleanly — but it would widen a mechanical patch into a schema change
across two artifact families, and the review-manifest generator
(`scripts/generate-rcap-review-manifests.mjs`) also reads these blocks. The
recorded decision is `BLOCKER-4-TERMINALIZATION-DECISION-MATRIX.md` §5,
per record, and the commit applying the patch should cite it. If the captain
prefers the decision inline in each record, that is a separate, wider patch and
this lane has not prepared it.

capturing `git diff`, and reverting. The worktree was confirmed clean
(`git status --porcelain` empty except this lane's untracked docs) before and
after.

## How to apply it, when someone decides to

```
git apply --check docs/rcap/grade-a/lane-j/patches/blocker-4-decision-unchanged-repin.patch
git apply         docs/rcap/grade-a/lane-j/patches/blocker-4-decision-unchanged-repin.patch

```

The patch is anchored at base `148382ab`. If the captain tip has moved a
compiled profile since, `git apply --check` will say so and the target hashes
must be recomputed rather than forced — a target hash is a statement about the
file that exists, and re-taking it is the whole point of the exercise.

## What this patch is not

It does not open payment, packet capability or commercial admission for any
route. Every one of the ten tracks is absent from
`route-ratification-registry.json`, has no record in
`data/rcap-ledger/packet-fulfillment-records.json`, and is denied by
`assertPacketFulfillmentProven`, which fails closed on a missing record.
`commerciallyEligible` is 0 before the patch and 0 after it.
