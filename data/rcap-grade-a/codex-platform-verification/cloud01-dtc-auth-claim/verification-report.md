## Defects

### CLOUD01-01 — Password reset drops the pending-result continuation

**Exact reproduction**

1. Start with the current-head DTC sign-in URL after anonymous screening, for example:
   `/expungement-ai/sign-in?mode=signin&claim=<valid-opaque-token>`.
2. Select **Forgot your password?**.
3. Inspect the destination generated by the current component. The link is the constant
   `/auth/forgot-password?product=expungement`; it does not carry `claim` or the current safe `next` value.
4. Submit the forgot-password form. `passwordResetRedirectTo()` passes only `product` and `hostname` to `passwordResetRedirectUrl()`.
5. Observe that the reset email target is always `/auth/set-password?next=/briefcase` for DTC. The callback therefore has no claim token for `claimExpungementPending()` and cannot atomically claim or redirect to the exact matter.

**Expected result**

The opaque claim token and safe continuation survive the forgot-password request and reset callback; after the verified recovery session is established, the server claims the pending result exactly once and redirects to `/briefcase/matters/<claimed-matter-id>`.

**Actual result**

The forgot-password link discards the token before the reset request. The reset callback receives only `next=/briefcase`, so it lands generically without claiming the waiting result.

**Affected paths/symbols**

- `src/components/expungement-ai/ConsumerSignInForm.tsx` — constant forgot-password `Link`.
- `src/app/auth/forgot-password/page.tsx` — `passwordResetRedirectTo()`.
- `src/lib/app-url.ts` — `passwordResetRedirectUrl()`.
- `src/app/auth/set-password/page.tsx` — `claimExpungementPending()` has correct consumption behavior but receives no token on this journey.

**Security or user impact**

The pending result is not improperly claimed, so ownership is not weakened. However, a participant who uses password recovery loses the required atomic-claim journey, does not receive the exact matter, and can arrive at an empty or unrelated generic Briefcase. This violates the exact-continuation and exact-redirect contract and creates conversion/data-continuity loss.

**Smallest bounded patch**

Preserve only the already-validated opaque claim token and a safe in-app `next` value when constructing the forgot-password link; have the forgot-password page pass those values through `passwordResetRedirectUrl()`; have that helper encode them into the DTC `/auth/set-password` URL. Continue using `safeAppRedirectPath` and `isWellFormedClaimTokenValue`; do not persist the token in browser storage and do not change authentication or claim authority.

**Focused regression test**

Extend `scripts/verify-expungement-forgot-password-domain.mjs` with a pure-helper case asserting that a valid DTC claim token and safe next path survive exactly into the Expungement.ai reset URL, while malformed tokens and external next URLs are omitted/rejected. Add a browser test starting at the DTC sign-in URL, following Forgot Password, stubbing `resetPasswordForEmail`, and asserting its `redirectTo` contains the same valid claim token and safe continuation. Complete a local Supabase recovery callback and assert one matter plus the exact matter redirect.
